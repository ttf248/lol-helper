# 历史战绩分析改造方案

## 目标

主页历史战绩页和对局内战绩页使用同一套历史事实数据与分析结果：

```text
PostgreSQL 缓存 ─┐
                 ├─ gameId 去重、身份校验、完整度判断 ─ 分析快照 ─┬─ 主页完整分析
接口最新分页 ────┘                                             └─ 对局内快速摘要
```

当前历史数据只会按 `modeKey` 统计，默认分析最近 100 场。接口用于补充最新记录，
数据库用于保存长期历史和优先渲染；两者不能因为请求先后顺序改变统计结果。

## 统一事实口径

每个对局以 `gameId` 唯一，排序使用 `gameCreation DESC, gameId DESC`。参与者身份按
`puuid -> summonerId -> 规范化召唤师名` 匹配，并记录匹配方式。完整队伍关系只允许使用
同一局中存在完整参与者且 `teamId` 可确认的数据。

接口与缓存合并时：

1. 先按模式读取 PostgreSQL 最近 100 场，立即展示缓存结果；
2. 继续请求接口分页，直到碰到本地 `gameId` 边界或达到扫描上限；
3. 同一个 `gameId` 优先保留参与者更完整、创建时间有效的数据；
4. API 的摘要数据不能覆盖数据库中已有的完整参与者数据；
5. 所有分析结果携带来源、样本量、完整度和置信度。

## 页面职责

### 主页历史分析

用于完整复盘：模式筛选、20/50/100 场窗口、胜率趋势、英雄/位置表现、常玩队友、
2/3/4/5 人组合排行、历史交手、关系网络、数据质量与导出。

### 对局内战绩

用于快速决策：先展示本地缓存，后台同步接口；只展示本局 10 名玩家的近期胜率、
已知组合、当前队伍协同、敌方风险和明确的缺失原因。完整关系网络和大表格留给主页。

## 分阶段提交

1. 统一数据来源、完整度和合并规则；
2. 主页增加常玩队友/最佳队友及组合排行筛选；
3. 主页增加位置、英雄、队友三维协同分析；
4. 对局内增加缓存优先的快速摘要和当前阵容关系卡片；
5. 增加 PostgreSQL 派生统计与数据库汇总刷新；
6. 增加分析快照导出和可复现证据。

每个阶段单独验证 TypeScript、前端构建和 Debug 构建后提交，避免接口、缓存和界面
改动混在同一个提交中。
